## 항목
### T-01 🔴 발주 상태(order_status) 읽고-합치고-쓰기에 잠금이 없음 + 잠금값을 못 읽음
- 근거: est-utils.js 약 540~578행. 고객 행을 `select=order_status`로만 읽은 뒤 병합해 `PATCH customers?id=eq.` 로 보냄(updated_at 조건 없음). 같은 코드에서 `rows[0].updated_at`을 읽으려 하지만 select에 없어 항상 비어 있음 → 공용 잠금 장부 기록이 항상 null.
- 같은 구멍이 대시보드 쪽에도 있음: dash-customer-order.js `saveOrderState`는 이 기기 캐시의 발주 현황 **전체**를 `saveCustomerFieldsToDb`로 보냄(메모·금액에는 있는 'CAS'(내가 본 값과 같을 때만 반영) 없음). 낡은 캐시를 가진 기기가 다른 기기의 발주 체크를 지울 수 있음.
- 기존 점검표(2026-10-15 동시접속 쓰기지점 점검표)에는 발주 현황 항목이 없었음 → 이번에 새로 드러난 빈칸.
- 위험: 두 화면(대시보드 발주 체크 + 견적서 앱 기록)이 동시에 쓰면 한쪽 발주 체크가 사라질 수 있음. 단계 규칙(시공준비중 이동)이 발주 체크를 보게 되므로 단계에도 영향. 잠금값이 null이라 열려 있는 대시보드에서 가짜 충돌이 날 수 있음.
- 완료 기준: select에 updated_at 포함, PATCH에 updated_at 조건 또는 DB 쪽 병합 함수 사용, 충돌 시 재시도/알림, 동시 쓰기 시험 1건 추가(tests/에 파일명 기록).

### T-02 🟡 견적서 앱의 고객 저장(est-save-stages.js 약 103행)이 updated_at 조건 없이 PATCH
- 근거: URL이 `customers?id=eq.<id>` 뿐. 10-15 점검표에는 '관찰 중(낮음)'으로 이미 기록됨. 바꾼 칸만 보내는지(P3 원칙)와 대시보드 동시 저장 시 영향은 아직 확인 못 함.
- 판정(2026-10-25 코드 확인): 이 PATCH가 보내는 칸은 이름·전화·주소(기본/상세)·실측일·시공일(및 미정 표시)·price·performance_revenue뿐(est-save-stages.js 178~257행). 고객 전체를 보내지 않으므로 메모·입금·단계·발주를 지울 수 없음. price·performance_revenue는 저장 직전 모든 견적서를 다시 합산한 값이라 스스로 정합. 남는 위험은 **날짜 칸**: 오래 열어 둔 견적서 화면의 옛 실측일·시공일이 그 사이 대시보드에서 바꾼 날짜를 덮어쓸 수 있음.
- 결정: 🟡 유지(관찰). 수정하지 않음. 이유: 수정 시각 조건을 걸면 견적서 저장이 자기 자신의 갱신과 부딪혀 '가짜 충돌'이 다시 나는 이력이 있음(10-11 장부 도입 기록). 대신 완료 기준을 '날짜 덮어쓰기 감지'로 바꿈: 날짜가 서버 값과 다른 채 저장되려 하면 경고하는 방안을 다음 점검 때 설계(승인 필요 여부는 그때 판단).
- 현재 증거: 오늘까지 날짜 덮어쓰기 사고 보고 없음(확인 방법: customer_history에서 measure_date/install_date 변경 직후 반대 변경 쌍 조회 — 아직 안 해봄, 다음 작업).

### T-03 🟡 구글 스크립트 복구 드릴·스키마 진단이 운영 DB에 서비스 키로 테스트 고객 생성 후 "보관 처리"
- 근거: apps-script-daily-backup.js 873~915행, 963~1006행. 정리 단계가 실패하면 테스트 고객이 운영 DB에 남음. 주석의 "DELETE가 RLS로 막힘"은 현재 정책(완전삭제 허용)과 맞지 않음.
- 현재 운영 잔존: "테스트 고객" 보관 2건(10-01 생성, 드릴 아님). 드릴 잔존 0건.
- 완료 기준: 정리를 정확한 id로 삭제, 잔존 점검 규칙 추가, 주석 정정.

## v1 추가분 (2026-10-25, DB 트리거·권한·점검 규칙 읽기 전용 조회)

### T-01 상태 갱신
- 수정 완료(커밋 17bbb32, push 대기): 대시보드는 서버 값에 바꾼 항목만 합쳐 수정시각 조건으로 저장, 견적서 앱은 수정시각 조건 + 1회 재시도. 시험: tests/order-status-concurrent-check.js, tests/est-order-status-lock-check.js.

### T-04 🟡 app_settings INSERT가 로그인한 누구나 가능 (UPDATE는 마스터 한정)
- 근거: pg_policies. app_settings_update는 마스터만, app_settings_insert는 `auth.uid() is not null`. 이미 있는 키는 못 바꾸지만 새 키는 추가 가능.
- 정정: 이전에 "app_settings 쓰기를 마스터로 조이기"라고 적은 것은 UPDATE가 아니라 INSERT가 대상. master_pw 삭제는 별도로 필요.
- 완료 기준: INSERT도 마스터 한정(월요일 SQL 묶음에 포함, 승인 필요).

### T-05 🟡 surveys UPDATE·as_records 전체가 로그인한 누구나 가능 (기존 S4)
- 근거: pg_policies. 개인정보 범위 결정(선혜님) 대기.

### T-06 🟢 WITH CHECK 없는 UPDATE 정책 (customers, estimates, extra_pay 등)
- 근거: pg_policies. customers·estimates는 trg_guard_staff_name_* 트리거로 담당자 변경을 막고 있음(S1·S2 처리). extra_pay UPDATE는 마스터 한정. 현재 위험 낮음.

### T-07 🔴 매일 점검의 "중요 트리거 감시 목록"에 중요한 트리거들이 빠져 있음
- 근거: v_critical_triggers_status 정의에 11개 이름이 하드코딩. 운영에 있지만 목록에 없는 것: trg_estimates_confirm_guard(확정 보호), trg_customers_auto_stage(입금 시 단계), trg_adjust_customer_amounts_on_estimate_delete, trg_sync_customer_price, trg_customers_updated / trg_estimates_updated(수정시각 갱신 = 동시 수정 잠금의 기반), 추가결제 트리거.
- 위험: 이 트리거가 지워지거나 꺼져도 매일 점검이 알려주지 못함.
- 완료 기준: 목록에 위 트리거 추가 + "운영에 있는 사용자 트리거 전체와 목록 대조" 규칙(목록에 없는 트리거가 생기면 경고), 시험 추가. DB 뷰 변경이라 승인 필요.
