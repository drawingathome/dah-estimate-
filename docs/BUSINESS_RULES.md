# 업무 규칙 (돈·계약·권한) — 코드가 지켜야 하는 기준

이 문서는 "무엇이 맞는 숫자인가"를 한 곳에 적은 것입니다. 코드·DB·구글 스크립트·테스트는 모두 이 기준을 따라야 하고,
규칙을 바꿀 때는 **이 문서 → 코드 → 테스트** 순서로 함께 고칩니다. (마지막 갱신: 2026-10-14)

## 1. 계약과 단계
1. 선금(계약금)이 기록되지 않았으면 **계약 전**이다. 계약 전 고객에게 실측일·시공일을 미리 적어두는 것은 정상이며 챙길 대상이 아니다.
2. **입금이 기록된 견적서만 "계약 건"으로 센다.** 가견적은 한 고객에게 여러 개 낼 수 있고 매출에 합산하지 않는다.
3. 계약 전 고객의 금액은 **"예상 금액"(가장 최근 가견적 1건)** 으로 표시한다(칸반에 "예상" 표시). 매출·계약 건수에는 잡지 않는다.
4. 입금(>0)이 기록되면 DB가 단계를 "선금결제"로 자동 이동한다(트리거 `customers_auto_stage_on_deposit`).
5. 무료 협찬(인플루언서)은 금액 0원으로 기록한다(고객 칸에 협찬가를 매출처럼 남기지 않는다).

## 2. 돈 계산 (한 곳 기준)
| 항목 | 기준 | 구현 위치 |
|---|---|---|
| 받은 돈 | 견적서별 선금+잔금 **순입금액**(환불 반영 후)의 합 | `getAllEstPays` / `getReceivedAmount` (dash-utils.js) |
| 매출(성과매출) | **제품비용만**(레일·시공비·옵션 제외), **실제 결제 비율만큼만** 인식. 총액 상한 | `splitCustomerPayments` (dash-chart.js), DB 월 마감 독립 검산 |
| 현재 매출 | 이번 달 1일~오늘 누적 | |
| 이번 달 매출(전월 마감) | 지난달 확정 실적(월 마감 스냅샷) | `monthly_close` |
| 고객 칸 금액 | 입금된 견적서(계약 건) 합계. 입금된 견적서가 없으면 이번 견적서 금액(가견적 합산 안 함) | est-save-stages.js, DB 트리거 `sync_customer_payment_from_estimates` |
| 마스터/실장 | 동일 기준 | |

## 3. 환불·취소
1. 환불은 **마스터만** 등록한다(`register_refund`). 실장은 요청만 한다. 환불 기록(`payment_refunds`)은 추가만 가능(수정·삭제 불가, 취소는 `reverse_refund`로 반대 기록).
2. 환불은 입금 숫자를 덮어쓰지 않는다. 입금칸은 **순입금액**을 보관하고, 환불은 별도 장부에 남는다.
3. 매출·성과매출은 날짜순 "입금 +, 환불 −" 누계로 계산한다(입금한 달에 +, 환불한 달에 −).
4. 받은 돈이 환불로 0이 되면 **취소 계약**: 마지막 환불일이 속한 달에 계약 건수 −1(전환율은 입금한 달 기준 유지).

## 4. 권한
1. 마스터는 전체. 실장은 **본인 담당 고객·견적서만** 조회·수정(담당자 이름 = `staff_profiles.display_name`과 정확히 일치).
2. 실장은 담당자를 바꿀 수 없다(**미배정 고객을 본인 이름으로 가져가기만 가능**). 남의 이름으로 고객·견적서를 만들 수 없다.
3. 실장은 **이미 기록된 입금을 줄이거나 입금일을 바꿀 수 없다**(마스터에게 요청). 입금을 늘리는 것·새로 기록하는 것은 가능.
4. 보관(archived) 견적서에는 입금을 기록할 수 없다(먼저 보관 해제).
5. 삭제는 완전삭제(되돌릴 수 없음). 고객명을 정확히 입력해야 한다. 담당 실장은 본인 담당 건 삭제 가능.
6. 이 모든 권한은 **화면이 아니라 DB(RLS·트리거)가 최종 강제**한다.

## 5. 동시 수정
- 입금 저장은 "화면에서 본 선금·잔금이 서버 값과 같을 때만" 저장한다. 그 사이 다른 사람이 바꿨으면 저장을 멈추고 최신으로 다시 불러온다.
- 고객·견적서 일반 저장은 `updated_at` 낙관적 잠금으로 충돌을 감지한다.

## 6. 점검(자동 검산)과 알림
- DB가 **매일 한국시간 07:00** 에 `data_integrity_issues` 전체를 점검해 `integrity_daily_log`에 남긴다. 36시간 넘게 기록이 없으면 앱 상단과 이메일로 "멈춤" 경고.
- 구글 스크립트(`dahDailyBackup`)가 매일 백업과 함께 중복·정합성·핵심 트리거 존재·DB 점검 결과를 이메일로 알린다("확인함" 처리한 항목은 반복 알림 없음).
- 점검 규칙: 입금 초과(OVERPAID), 금액 다름(계약 이후 단계만, PRICE_DIFF), 성과매출 0 / 성과매출 > 총액 / 입금합계 불일치 등. 규칙을 추가하면 이 문서와 라벨(dash-integrity-watch.js)을 함께 고친다.
- 월 마감: 틀린 숫자로 마감하지 않는다. 마감 후 숫자가 바뀌면 마감 카드에 차이를 표시한다.

## 7. 알려진 한계
- 사람이 틀린 금액을 입력하는 것, 통장·카드사 기록과의 불일치는 **월 대조**로만 잡힌다(대조 기능은 아직 없음).
- 입금을 늘리는 입력은 권한으로 막을 수 없다(실장이 기록하는 일이므로).
- 마스터가 입금칸을 직접 고쳐 감액할 수는 있다(변경 이력에는 남는다). 환불은 "환불 등록"으로 하도록 유도한다.
