# 업무 규칙 (돈·계약·권한) — 코드가 지켜야 하는 기준

이 문서는 "무엇이 맞는 숫자인가"를 한 곳에 적은 것입니다. 코드·DB·구글 스크립트·테스트는 모두 이 기준을 따라야 하고,
규칙을 바꿀 때는 **이 문서 → 코드 → 테스트** 순서로 함께 고칩니다. (마지막 갱신: 2026-10-14)

## 1. 계약과 단계
1. 선금(계약금)이 기록되지 않았으면 **계약 전**이다. 계약 전 고객에게 실측일·시공일을 미리 적어두는 것은 정상이며 챙길 대상이 아니다.
2. **입금이 기록된 견적서만 "계약 건"으로 센다.** 가견적은 한 고객에게 여러 개 낼 수 있고 매출에 합산하지 않는다.
3. 계약 전 고객의 금액은 **"예상 금액"(가장 최근 가견적 1건)** 으로 표시한다(칸반에 "예상" 표시). 매출·계약 건수에는 잡지 않는다.
4. 입금(>0)이 기록되면 DB가 단계를 "선금결제"로 자동 이동한다(트리거 `customers_auto_stage_on_deposit`).
5. 무료 협찬(인플루언서)은 금액 0원으로 기록한다(고객 칸에 협찬가를 매출처럼 남기지 않는다).

## 2. 돈 계산 (한 곳 기준)
| 항목 | 기준 | 구현 위치 |
|---|---|---|
| 받은 돈 | 견적서별 선금+잔금 **순입금액**(환불 반영 후)의 합 | `getAllEstPays` / `getReceivedAmount` (dash-utils.js) |
| 매출(성과매출) | **제품비용만**(레일·시공비·옵션 제외), **실제 결제 비율만큼만** 인식. 총액 상한 | `splitCustomerPayments` (dash-chart.js), DB 월 마감 독립 검산 |
| 현재 매출 | 이번 달 1일~오늘 누적 | |
| 이번 달 매출(전월 마감) | 지난달 확정 실적(월 마감 스냅샷) | `monthly_close` |
| 고객 칸 금액 | 입금된 견적서(계약 건) 합계. 입금된 견적서가 없으면 이번 견적서 금액(가견적 합산 안 함) | est-save-stages.js, DB 트리거 `sync_customer_payment_from_estimates` |
| 마스터/실장 | 동일 기준 | |

## 3. 환불·취소
1. 환불은 **마스터만** 등록한다(`register_refund`). 실장은 요청만 한다. 환불 기록(`payment_refunds`)은 추가만 가능(수정·삭제 불가, 취소는 `reverse_refund`로 반대 기록).
2. 환불은 입금 숫자를 덮어쓰지 않는다. 입금칸은 **순입금액**을 보관하고, 환불은 별도 장부에 남는다.
3. 매출·성과매출은 날짜순 "입금 +, 환불 −" 누계로 계산한다(입금한 달에 +, 환불한 달에 −).
4. 받은 돈이 환불로 0이 되면 **취소 계약**: 마지막 환불일이 속한 달에 계약 건수 −1(전환율은 입금한 달 기준 유지).

## 4. 권한
1. 마스터는 전체. 실장은 **본인 담당 고객·견적서만** 조회·수정(담당자 이름 = `staff_profiles.display_name`과 정확히 일치).
2. 직원 표시 이름은 중복될 수 없고, 바꾸면 그 직원 담당 고객·견적서의 담당자 이름도 자동으로 같이 바뀐다. 담당자 이름이 직원 목록에 없는 고객은 점검 규칙 `ORPHAN_STAFF`로 잡힌다. (장기: 이름 대신 고유번호로 연결 — 직원이 늘기 전에)
2-1. 실장은 담당자를 바꿀 수 없다(**미배정 고객을 본인 이름으로 가져가기만 가능**). 남의 이름으로 고객·견적서를 만들 수 없다.
3. 실장은 **이미 기록된 입금을 줄이거나 입금일을 바꿀 수 없다**(마스터에게 요청). 입금을 늘리는 것·새로 기록하는 것은 가능.
4. 보관(archived) 견적서에는 입금을 기록할 수 없다(먼저 보관 해제).
5. 삭제는 완전삭제(되돌릴 수 없음). 고객명을 정확히 입력해야 한다. 담당 실장은 본인 담당 건 삭제 가능.
6. 이 모든 권한은 **화면이 아니라 DB(RLS·트리거)가 최종 강제**한다.

## 5. 동시 수정
- 입금 저장은 "화면에서 본 선금·잔금이 서버 값과 같을 때만" 저장한다. 그 사이 다른 사람이 바꿨으면 저장을 멈추고 최신으로 다시 불러온다.
- 고객·견적서 일반 저장은 `updated_at` 낙관적 잠금으로 충돌을 감지한다.

## 6. 점검(자동 검산)과 알림
- DB가 **매일 한국시간 07:00** 에 `data_integrity_issues` 전체를 점검해 `integrity_daily_log`에 남긴다. 36시간 넘게 기록이 없으면 앱 상단과 이메일로 "멈춤" 경고.
- 구글 스크립트(`dahDailyBackup`)가 매일 백업과 함께 중복·정합성·핵심 트리거 존재·DB 점검 결과를 이메일로 알린다("확인함" 처리한 항목은 반복 알림 없음).
- 점검 규칙: 입금 초과(OVERPAID), 금액 다름(계약 이후 단계만, PRICE_DIFF), 성과매출 0 / 성과매출 > 총액 / 입금합계 불일치 등. 규칙을 추가하면 이 문서와 라벨(dash-integrity-watch.js)을 함께 고친다.
- 월 마감: 틀린 숫자로 마감하지 않는다. 마감 후 숫자가 바뀌면 마감 카드에 차이를 표시한다.

## 7. 알려진 한계
- 사람이 틀린 금액을 입력하는 것, 통장·카드사 기록과의 불일치는 **월 대조**로만 잡힌다. 설정 > "입금 대조"(마스터 전용)에 통장 내역을 붙여넣으면 앱 기록과 1:1로 맞춰 "통장에만 있음 / 앱에만 있음 / 일치"를 보여준다(읽기 전용, 서버로 전송 안 함). 카드 정산(수수료·합산 입금)은 1:1로 안 맞을 수 있다.
- 입금을 늘리는 입력은 권한으로 막을 수 없다(실장이 기록하는 일이므로).
- 마스터가 입금칸을 직접 고쳐 감액할 수는 있다(변경 이력에는 남는다). 환불은 "환불 등록"으로 하도록 유도한다.


## 견적서 삭제와 받은 돈 (2026-10-14 추가)
- 견적서를 지우면 고객의 금액·성과매출은 그 견적서 몫만큼 줄지만, 고객 칸의 입금 기록은 "받은 돈이 사라지지 않게" 큰 값을 유지한다(DB 트리거 `sync_customer_payment_from_estimates`의 GREATEST).
- 그래서 입금이 있던 견적서를 마지막으로 지우면 "입금은 있는데 견적서가 없는" 고객이 남을 수 있고, 점검 규칙 `PAID_NO_ESTIMATE`가 잡는다. 받은 돈이 실제로 환불된 것이면 마스터가 환불 등록으로 정리한다.
- 견적서가 여러 건일 때 하나를 지우면 고객 칸이 더 크게 남아 `PAY_SUM_MISMATCH`로 잡힌다.
- 삭제는 운영 DB에서 모의 실행이 막혀(자동 취소) 코드 분석과 기존 테스트(`estimate-delete-refreshes-customer-check.js`)로만 확인함.


## 입금 대조와 카드 수수료 (2026-10-15 추가)
- 앱에 기록된 입금 금액은 고객이 낸 금액(수수료 차감 전)이다. 카드 수수료는 매출이 아니라 비용으로 따로 본다.
- 카드 정산 입금은 수수료가 빠지고 여러 건이 합쳐 들어올 수 있어 통장과 1:1로 안 맞는다. 그래서 대조는 두 갈래로 한다: ① 계좌이체·현금 = 통장 내역 ② 카드 = 결제선생/토스/카드사 "승인 내역"(승인금액=앱 금액, 수수료 허용 0%).
- 정산 입금을 건별로 받는 경우에 한해 "카드 수수료 허용(%)"으로 수수료만큼 적은 금액을 일치로 본다. 합산 정산은 지원하지 않음(승인 내역 대조로 대신함).


## 권한과 자동 시험 (2026-10-15 추가)
- 실장은 본인 담당 고객·견적서만 보고 고칠 수 있고, 남의 고객을 가져가거나 삭제할 수 없다(DB가 강제).
- 이 규칙이 깨지지 않았는지 매일 06:55 `staff_permission_selftest()`가 실장 계정으로 직접 시도해 본다(실데이터는 바뀌지 않음). 실패하면 대시보드 점검 카드에 빨간 경고.
- 점검 뷰(`data_integrity_issues`)를 `create or replace` 하면 `security_invoker` 옵션이 초기화된다 → 반드시 `alter view ... set (security_invoker = true)`를 같이 실행(정적 검사 `view-security-invoker-check.js`, 매일 시험 둘 다 감시).
- 입금이 기록된 고객이 삭제되면 30일 동안 점검 카드에 "입금 있던 고객 삭제됨"으로 뜬다(이력에서 복구 가능).


## 점검·알림 규칙 한 곳 목록 (2026-10-15, 계획 2-8)
**정의는 DB 뷰 `data_integrity_issues` 한 곳**이고, 화면 이름은 `dash-integrity-watch.js`의 `INTEGRITY_LABELS` 한 곳이다. 코드와 이름이 하나라도 어긋나면 `integrity-rule-labels-check.js`가 실패한다. 규칙을 새로 만들 때는 ① 뷰에 추가 ② 이름표 추가 ③ 이 목록에 추가, 이 세 가지를 같이 한다.

| 코드 | 화면 이름 | 뜻 |
|---|---|---|
| NO_ESTIMATE | 견적서 없음 | 계약 이후 단계인데 연결된 견적서가 없음 |
| PAID_STAGE_NO_DEPOSIT | 입금 기록 없음 | 선금결제 이후 단계인데 받은 돈이 0 (판정은 DB 함수 `dah_received_amount`) |
| DONE_NO_INSTALL_DATE | 시공일 없음 | 시공완료인데 시공일이 비어 있음 |
| OVERPAID | 입금 초과 | 받은 돈이 견적금액보다 많음(환불 등록 필요 여부 확인) |
| NO_STAFF | 담당자 없음 | 담당자가 비어 있음 |
| ORPHAN_STAFF | 담당자 연결 끊김 | 담당자 이름이 직원 목록에 없음 |
| MULTI_FINAL | 확정견적 중복 | 한 고객에 확정 견적서가 둘 이상 |
| ORPHAN_ESTIMATE | 고객 없는 견적서 | 견적서의 고객이 없음 |
| HIDDEN_ESTIMATE | 숨김 견적서 | 보관(숨김)된 견적서가 살아 있는 고객 금액에 영향 |
| PRICE_DIFF | 금액 다름 | 고객 금액과 확정 견적서 금액이 다름(계약 이후 단계만) |
| PERF_ZERO_WITH_PAYMENT | 성과매출 0 | 입금이 있는데 성과매출이 0 |
| PERF_OVER_PRICE | 성과매출 > 총액 | 성과매출이 견적 총액보다 큼 |
| PAY_SUM_MISMATCH | 입금합계 불일치 | 고객 칸 입금과 견적서 입금 합계가 다름 |
| PAID_NO_ESTIMATE | 입금 있는데 견적서 없음 | 입금은 있는데 살아 있는 견적서가 없음 |
| PAID_CUSTOMER_DELETED | 입금 있던 고객 삭제됨 | 입금이 있던 고객이 삭제됨(30일간 표시) |

나머지 알림의 정의 위치(모두 한 함수가 정의하고 화면은 그 함수만 호출):
- 미수금·잔금: `getUnpaidAmount` (고객 목록 칩, 미수금 필터, 홈 처리필요, 성과 비교 모두 이 함수)
- 계약 여부: `isContractedCustomer` / DB `dah_is_contracted`
- 마스터 여부: `isMasterUser()` (화면 숨김용, 진짜 차단은 DB 권한)
- 자동 점검 멈춤(36시간)·권한 자동 시험 실패: `dash-integrity-watch.js`의 `_integrityAutoNote`
