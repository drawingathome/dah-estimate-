# 운영 데이터 수정 절차 (돈·고객 데이터를 직접 고칠 때)

화면이 아니라 DB를 직접 고쳐야 할 때(데이터 정정, 백필 등)의 표준 절차입니다. 한 번에 한 건, 되돌릴 수 있게.

1. **읽기 전용으로 먼저 확인**: 고칠 행과 영향 범위(월 매출·계약 건수·다른 고객)를 SELECT로 확인한다.
2. **수정 전 값을 기록**: 고치는 값은 `claude/날짜-데이터정정-기록.md`(프로젝트 문서)에 "수정 전 → 수정 후"로 남긴다. 변경 이력 표(`customer_history`·`estimate_history`)는 트리거가 자동 기록하지만, 사람이 읽을 근거도 따로 둔다.
3. **스냅샷이 필요한 큰 수정**(여러 건·계산 필드): 먼저 `표이름_backup_YYYYMMDD` 사본을 만들고 **같은 명령에서 반드시 `ENABLE ROW LEVEL SECURITY`** 를 켠다(안 켜면 외부에서 조회 가능). 작업이 끝나 더 쓸 일이 없으면 Supabase 화면에서 삭제한다(운영 DB의 DROP/DELETE는 자동 차단되므로 사람이 한다).
4. **모의 실행**: 트리거·함수·정책 변경은 `DO $sim$ … RAISE EXCEPTION 'SIM: %' $sim$` 블록으로 실행해 결과만 보고 **전부 롤백**되게 한다. 사용자 흉내는 `set_config('request.jwt.claim.sub', '<uid>', true)`.
5. **적용**: DDL은 `apply_migration`(파일은 저장소에 `migration_날짜_이름.sql`로도 남긴다). 데이터 수정은 한 건씩 조건(`where id = …`)을 정확히.
6. **재검산**: 수정 직후 `data_integrity_issues`, 월 매출, 고객 합계 vs 견적서 합계를 다시 조회해 의도한 변화만 있는지 확인한다.
7. **기록 마무리**: 정정 기록 문서에 결과를 적고, 이영욱처럼 "확인함"이 필요한 점검 항목은 대시보드에서 처리한다.

주의
- 이미 마감한 달의 숫자가 바뀌는 수정은 마감 카드에 차이로 표시되므로, 마감 전에 정리하는 것이 원칙.
- 환불·입금 취소는 직접 UPDATE가 아니라 마스터 화면의 "환불 등록/취소"를 쓴다(장부가 남는다).
- 운영 DB에서 DROP/DELETE가 자동 취소되는 것은 안전장치이므로 우회하지 않는다.
